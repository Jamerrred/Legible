# MuseFront project overview

*Last updated 5 November 2026. The first local demo is built on one mock business: see [the benchmark](../reports/first-demo-benchmark.md). The back office agent's backend is built as a prototype: see [its report](../reports/back-office-mvp.md).*

## In one sentence

MuseFront gives a service business a small website that any AI agent can read and act on, plus a back office agent that keeps that website accurate.

## The problem

AI agents acting for people already land on small business websites, and they often can't finish the job. Prices, availability and rules are missing, buried or hidden behind forms, so the agent reports "unverified" or tells the person to call.

The business can't see this happening. To the owner, it looks like bot traffic or an abandoned session.

The founder's test with Muse shows the problem on one real query ([details](02-muse-findings.md)). It's one example, not the boundary of the product: the roadblocks we design for are much wider ([list](05-roadblocks-and-queries.md)).

## The goal right now

A compelling, functional demo on mock businesses. There's no pilot with real businesses and no time limit on the build.

"Functional" means real agents, real websites and real endpoints. Only the businesses and their back-end data are mock.

## Decisions

| Topic | Decision |
|---|---|
| Goal | Demo on mock businesses, with no pilot and no time limit |
| Breadth | Horizontal, for any business type. The demo set is four service businesses, starting with one |
| Agents served | All kinds: personal agents (Muse, Instinct, ChatGPT agent, Grok), search APIs (Exa, Tavily, Parallel) and fetch tools |
| Priority | Legibility first, purchases later |
| Out of scope | How an agent finds the business in the first place |
| Placement | One link that can go on a website or social profile |
| Consumer agent | Build our own stand-in, learning from open-source research and browser agents |
| First resource | Written by Claude as a static page, not generated by the back office agent, to test before and after |
| Back office agent | Built end to end: ingestion, Composio connectors, simulation, owner inbox, and revision in plain language. Its output is the resource |
| Front desk agent | **Dropped** |
| Connector application to Meta | **Dropped** |
| MCP and Poppy | Optional, and only after the back office agent |
| Owner account connectors | Composio |
| Website crawling | Exa, with a plain crawl as backup. This replaced Context.dev on 5 November |
| Simulation | One check at onboarding, then a periodic review of real agent activity |
| Hosting | The resource on a Cloudflare Worker with D1. The back office runs separately |
| Roadblocks and queries | Wide and long-tail, not modelled on the van cleaning example alone |

## Proposed, not yet confirmed

- **Test rules:** the fairness rules in [the build plan](03-build-plan.md#test-rules).
- **Resource address:** a subdomain of the business's own domain, such as `agents.example-business.com`, rather than `slug.musefront.ai`.
- **Technical choices:** the stack in [the consumer agent design](08-consumer-agent-design.md).
- **Demo target:** the agent fails before and succeeds after in at least 8 of 10 runs. This is a proposed number, not one taken from data.
- **Extras:** an agent's-eye view that shows what each agent type receives, and owner-set offers such as a bounded off-peak discount.

## What replaced what

If you've read older material from this project, these are the changes.

| Earlier position | Current position | Why |
|---|---|---|
| Build a front desk agent that talks to outside agents | Dropped | By its own account, Muse reads pages and fills in forms. It has no way to discover and talk to a business's agent |
| Apply to Meta's connector program | Dropped | Not needed for the demo, and acceptance is uncertain |
| Hosted at `slug.musefront.ai` by default | Prefer the business's own subdomain | Muse says "merchant's own site beats aggregator", so our domain could read as a third-party listing |
| Demo set: car wash, HVAC and an online store | Four service businesses | The founder's direction on 4 November |
| MCP and Poppy are core parts of the resource | Optional, and later | The Muse findings point to pages and forms first |
| Roadblocks drawn from one image-pricing car wash, then one van cleaning query | A wide catalogue across many service types | The founder's direction on 4 November |

## How it fits together

Think of a shop. The resource is the sign in the window, the business record is the manager's notebook, the agent is the staff, and the harness is the equipment and rulebook the staff work with.

```
SOURCES                          BACK OFFICE AGENT             OUTPUT

Website (Exa)            --->    Proposes changes     --->     Business record
Owner accounts (Composio)        Asks the owner                facts, offerings,
Files and interview              Applies instructions          actions, rules
Owner instructions               Runs the simulator                  |
                                 Learns from activity                v
                                        ^                      Resource (the "slug" site)
                                        |                      page, forms, markdown
                                  Activity log                       |
                                        ^                            v
                                        +------- requests -----  Any consumer agent
                                                 questions

Owner inbox: confirms each change the agent proposes, and approves requests.
```

Three rules hold across this:

- **The agent changes the record, never the page.** The resource regenerates from the record, so its parts can't disagree.
- **Only confirmed facts are served.** Nothing an outside agent sends can change the record without the owner confirming.
- **The resource doesn't depend on a live model.** If the LLM goes down, the page and forms keep working.

## The parts

| Part | What it does | When |
|---|---|---|
| Mock businesses | Four public websites with realistic roadblocks | First |
| Consumer agent | Our stand-in for real agents, in several profiles | First |
| Resource | The page, forms and markdown an agent reads ([spec](04-resource-spec.md)) | Hand-written first, then generated |
| Business record | Single source of truth for facts, offerings, actions and rules | With the back office agent |
| Ingestion | Turns the website, files, interview and connected accounts into proposed facts | With the back office agent |
| Back office agent | Keeps the record current ([spec](09-back-office-agent.md)) | After the before-and-after test works |
| Owner app and inbox | Where the owner chats with the agent, confirms changes and handles requests | With the back office agent |
| Request handling | Receives quote and booking requests, enforces owner rules in code | Basic version first, full version with the back office agent |
| Simulator | Runs the consumer agent against a resource to find gaps | Reuses the consumer agent |
| Activity log and learning | Records what agents did and turns gaps into owner questions | Logging from day one, learning with the back office agent |
| Attach kit | The link and copy-paste facts for the owner's site and social profiles | Basic version first |
| MCP and Poppy | Direct machine connections | Optional, at the end |
| Payments | A payment link handoff | Later, not needed for legibility |

## Agent types to serve

| Type | Examples | How it sees a business | What the resource must offer |
|---|---|---|---|
| Search APIs | Exa, Tavily, Parallel | Excerpts or markdown | Self-contained facts, so one snippet is enough |
| Fetch tools | Claude web fetch, coding agents | Plain requests, often without JavaScript | Content in the HTML, a markdown version, visible URLs |
| Browser agents | Muse's browser agent, ChatGPT agent | A rendered page | Real forms that work without personal details until booking |
| Connected agents | Claude or ChatGPT connectors | Tool calls | `/mcp`, optional and later |

## The demo story

1. **Before:** a consumer agent tries a realistic request on a mock business and can't verify the answer.
2. **Onboarding:** the back office agent reads the business's site and proposes facts, and the owner confirms them.
3. **Hardening:** the simulator finds gaps, the owner answers them one at a time, and the score rises.
4. **After:** the same agent and prompt now succeed. A request reaches the owner's inbox and the owner approves it.
5. **Learning:** an agent asks something unknown, the owner answers once, and the next agent gets the answer.
6. **Breadth:** the same flow runs on the other three businesses, with different kinds of requests.

## Is it validated?

Not yet.

| Question | Status | Why |
|---|---|---|
| Do agents struggle with these businesses? | Supported, but thin | Muse couldn't verify a price and slot, though that's one query, one agent and its own account |
| Would an agent use a MuseFront resource? | Partly tested | Our stand-in reached it in 11 of 12 local runs without being told it exists. Real agents haven't been tested |
| Would an agent treat it as the merchant's own information? | Not tested | It might read as a third-party listing |
| Would owners set it up and keep it updated? | Not tested | No owner has seen it |
| Would businesses get more customers? | Not tested | There's no data |

The demo and the Muse test can answer the second and third questions. The last two need real owners, which comes after the demo.

## Main risks and unchecked items

- **Link following:** an unmodified agent may never follow the link from the website to the resource. Step 5 of the build plan tests this.
- **Social links:** Instagram's `robots.txt` blocks compliant crawlers, and we found no evidence either way that agents follow bio links. Don't claim an agent got there that way unless we see it happen.
- **New sites and search:** a brand-new mock site probably won't appear in search results, so prompts give the agent the business's URL.
- **Tools still to check:** which services Composio can connect, and Poppy's exact field names against its validator.

## Glossary

| Term | Meaning |
|---|---|
| Consumer agent | An agent acting for a person who wants something from a business |
| Stand-in | Our own consumer agent, built to behave like the real ones |
| Resource | The small website MuseFront hosts for a business, written for agents and readable by people |
| Slug | A short, URL-safe version of a name: "Joe's HVAC" becomes `joes-hvac`. We also use it loosely to mean the resource |
| Business record | The database of a business's facts, offerings, actions and rules |
| Back office agent | The agent on our servers that keeps the record current, working with the owner |
| Front desk agent | A dropped idea: an agent that would have talked to outside agents |
| Simulator | The consumer agent run against a resource to find what's missing |
| Harness | The software around a model that runs an agent: its loop, tools, memory and permissions |
| MCP | A standard way for an agent to call a service's functions directly |
| Poppy | The Personal Agent Protocol from Sierra and Meta, announced in October 2026 and still a draft |
| Composio | A service for connecting an owner's accounts, such as a calendar |
